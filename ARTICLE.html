Building Permission-Aware RAG Caching on AWS

A working implementation with Bedrock, Valkey and DynamoDB, tested while permissions and source documents change.

bcfmtolgahan · October 2026

TL;DR I built a Bedrock answer cache that checks current DynamoDB permissions before returning a hit. Changing a grant or publishing a document changes which cache entries a request can use, without deleting the old entries. I compared three modes with 16 requests each: the semantic mode needed 3 generation calls, versus 16 without caching, with median service latency of 85 ms versus 541 ms. Those numbers come from a small, repeated workload. Race tests also showed the limit: revocation after the final authorization read can still race with delivery.

I generated a retention-policy answer for a user who could read internal documents. The answer said 90 days. Then I removed that user's internal access and asked the same question with the same Cognito token.

I had issued no cache deletion. The API accepted the same token and returned 30 days, from the public policy.

The same question now needed a different answer. A tenant ID in the cache key would not catch this change: two people in the same organization can have different document access. A user ID would isolate their entries, but that user's permissions can change too.

A RAG answer also depends on the document collection it was generated from. Rechecking the old source documents misses another case: a newly published document can change the correct answer even when every old source remains untouched.

I used DynamoDB to decide which source view was current, and included that view in the cache key. The code below comes from the accompanying repository, including the Terraform and the driver that tested permission changes against running Lambda invocations.

Two tenants, different retention policies

I used two synthetic organizations, acme and globex, with two products each. Public and internal policies deliberately disagree. Within a product, the model is instructed to use the authorized source with the highest numeric priority.

Fixture values for Atlas. “Public” is a document entitlement, not anonymous access.
TenantPublic policyInternal policyUsers

Boreal has different durations. Across both products and tenants, the fixture contains eight documents. Alice and Carol should be able to share an answer. Bob must not receive their internal answer. Dana must receive her own organization's policy even when her question is identical.

Each request is a single question. There is no private chat history or personalized prompt to carry into a shared answer.

The deployed AWS path

Amazon API Gateway validates the Amazon Cognito JWT before invoking AWS Lambda. The handler takes the subject from the verified authorizer context. Its request body accepts only question and mode; the caller cannot supply a tenant, grants, or a test hook.

The test driver sends a Cognito ID token, and this route has no OAuth scope requirement. An API intended to accept only access tokens needs the appropriate token and scope checks; configuring a JWT authorizer alone does not make that distinction. Here, the token supplies identity and DynamoDB supplies document permissions.

DynamoDB stores each user's current entitlements and each tenant's document manifest. Amazon S3 stores the source text and its embedding. ElastiCache stores generated answers, their provenance and the vectors used for semantic lookup.

On a miss, Lambda loads authorized source objects, checks their SHA-256 digests, ranks their stored embeddings against the query, and sends the text to Amazon Bedrock. The code scans those vectors in-process with top_k=8. A baseline user can see only two or four documents, so every authorized document fits in the prompt. This run exercises source filtering and answer reuse; it does not measure selective retrieval from a large corpus.

The stack ran in eu-central-1. Query and source embeddings used amazon.titan-embed-text-v2:0, with 256 dimensions and normalization enabled. Generation used Amazon Nova Micro through eu.amazon.nova-micro-v1:0. That is an EU cross-region inference profile, so generation can be routed to another supported EU region.

Read the principal and corpus together

In this experiment, revoking access means updating the user's DynamoDB grants. It does not mean revoking the Cognito token or signing the user out. The test deliberately keeps using the token issued before the permission change.

The authority table has a USER#<subject> item containing tenant, grants, enabled status and a monotonic revision. A TENANT#<tenant> item contains the corpus version and source metadata.

I first read the user consistently to discover the tenant key. Then I read that user and the corresponding tenant manifest in one TransactGetItems call:

src/ragcache/aws_adapters.py · lines 24–48
def snapshot(self, subject):
    try:
        first = self.client.get_item(TableName=self.table, Key={"pk": {"S": f"USER#{subject}"}},
                                     ConsistentRead=True, ReturnConsumedCapacity="TOTAL")
        self.rcu += first.get("ConsumedCapacity", {}).get("CapacityUnits", 0)
        if "Item" not in first:
            raise Denied("Unknown principal")
        hinted = self.unpack(first["Item"])
        tenant = hinted["tenant"]
        result = self.client.transact_get_items(TransactItems=[
            {"Get": {"TableName": self.table, "Key": {"pk": {"S": f"USER#{subject}"}}}},
            {"Get": {"TableName": self.table, "Key": {"pk": {"S": f"TENANT#{tenant}"}}}},
        ], ReturnConsumedCapacity="TOTAL")
        self.rcu += sum(x.get("CapacityUnits", 0) for x in result.get("ConsumedCapacity", []))
        if any("Item" not in x for x in result["Responses"]):
            raise Denied("Missing authority record")
        user, corpus = [self.unpack(x["Item"]) for x in result["Responses"]]
        if user["tenant"] != tenant or corpus["tenant"] != tenant:
            raise Denied("Principal routing changed")
        return Snapshot(subject, tenant, int(user["version"]), int(corpus["version"]),
                        tuple(sorted(user["grants"])),
                        tuple(DocumentRef(**{**d, "priority": int(d.get("priority", 0))})
                              for d in corpus["documents"]), bool(user["enabled"]))
    except (ClientError, BotoCoreError, KeyError, TypeError, ValueError) as exc:
        raise Unavailable("Authority unavailable or malformed") from exc

The first read is a routing hint. If the user moves tenants before the transaction, the tenant comparison rejects the request. Otherwise, the transactional read supplies the user and corpus state used for the decision.

I used a transaction because independent reads can straddle a concurrent update. DynamoDB documents serializable isolation for transactional reads against standard writes. This gives the application a defined snapshot for those two items. It does not lock them for the duration of the model call.

The same operation runs again before returning the answer. A successful request therefore performs two routing reads and two two-item transactions. That cost remains on cache hits.

What belongs in the cache key

The cache scope is a SHA-256 hash of the tenant, corpus version, sorted grants, pipeline fingerprint and visible document metadata:

src/ragcache/core.py · lines 87–95
def scope_id(self, pipeline: str) -> str:
    # Users can share only an identical current, non-personalized view.
    # Principal revision is checked separately so equal entitlements share.
    return digest({
        "tenant": self.tenant, "corpus": self.corpus_version,
        "grants": sorted(self.grants), "pipeline": pipeline,
        "visible_documents": sorted((d.doc_id, d.version, d.sha256, d.scope, d.topic,
                                     d.key, d.priority) for d in self.allowed),
    })

The document metadata includes scope, topic and priority as well as the object key, content hash and version. A changed priority can alter the answer even if the document text is unchanged.

The user ID and principal revision are deliberately absent from this shared key. Alice and Carol have the same current, non-personalized source view, so they can reuse the same entry. The principal revision is checked separately in a request-specific authorization stamp. Removing and restoring a grant during a request still changes that revision.

Exact matching hashes the original question string:

src/ragcache/aws_adapters.py · lines 120–121
def key(scope, question):
    return f"ragcache:{scope}:{digest(question)}"

I do not lowercase arbitrary questions for exact matching. Case normalization can change meaning, such as US versus us. Normalization is limited to the small semantic-admission grammar described below.

The pipeline fingerprint also makes configuration part of the cache namespace:

src/handler.py · lines 26–29
pipeline = digest({"prompt": "authorized-retention-v1", "model": model_id,
                   "embedding": "amazon.titan-embed-text-v2:0", "dimensions": 256,
                   "contract": "bounded-retention-v1", "top_k": 8,
                   "threshold": threshold, "temperature": 0, "max_tokens": 160})

The fingerprint relies on declared contracts. If I change prompt semantics or retrieval behavior, I must bump the corresponding version. Keeping the same label while changing its meaning can reuse an incompatible answer; the hash cannot detect an undeclared code change.

The scope filter is followed by a second check on the decoded entry:

src/ragcache/core.py · lines 113–120
def valid_for(self, snapshot: Snapshot, pipeline: str, scope_id: str) -> bool:
    allowed = {(d.doc_id, d.version, d.sha256) for d in snapshot.allowed}
    dependencies = {(d["doc_id"], d["version"], d["sha256"]) for d in self.dependencies}
    return (
        self.scope_id == scope_id and self.tenant == snapshot.tenant
        and self.corpus_version == snapshot.corpus_version and self.pipeline == pipeline
        and bool(dependencies) and dependencies <= allowed
    )

This checks the tenant, pipeline, corpus and source dependencies independently of the Valkey search filter. It assumes a trusted publisher and cache writer. The cache records are unsigned.

When a new document changes an old answer

An answer's dependency list contains every document passed to the model. It does not depend on which documents the model chooses to cite.

A source can influence the generated text without appearing in a citation. Recording the entire input set lets the final check ask whether all of those source versions remain authorized.

That still leaves additions. In one test, Bob's public Atlas policy said 30 days. I added a higher-priority public amendment saying 45 days. The original document was unchanged. An implementation that only rechecked the old dependency would accept the old answer.

Here, publishing any document change increments the tenant's corpus version. The new version produces a new cache namespace, including when a newly added source was absent from every previous dependency list.

scripts/lab.py · lines 112–126
def publish(self, tenant, documents):
    pk = f"TENANT#{tenant}"
    old = self.get(pk)
    version = int(old["version"]) + 1 if old else 1
    item = {"pk": pk, "tenant": tenant, "version": version, "documents": documents}
    # All immutable S3 objects already exist. Publishing the manifest is a
    # single conditional authority write; partial uploads are never active.
    if old:
        self.ddb.put_item(TableName=self.r["table"], Item=encode(item),
            ConditionExpression="#v=:old", ExpressionAttributeNames={"#v": "version"},
            ExpressionAttributeValues=encode({":old": old["version"]}))
    else:
        self.ddb.put_item(TableName=self.r["table"], Item=encode(item),
            ConditionExpression="attribute_not_exists(pk)")
    return version

The publisher uploads objects under documents/<tenant>/<document>/<sha256>.json before conditionally replacing the manifest. Concurrent publishers must match the prior version. A failed manifest update can leave an unused object, but that object is not visible to retrieval.

“Immutable” here means content-addressed and hash-verified by the application. S3 Object Lock and bucket versioning are not enabled. I tested the distinction by overwriting a fixture object: a fresh retrieval returned 503 before those bytes reached the model. A warm answer still represents its earlier verified source until the manifest changes.

The tenant-wide version costs hit rate: even an unrelated or invisible document update changes the namespace. Finer partitions would need to account for newly relevant documents as well as changed dependencies. The single manifest also has DynamoDB's 400 KB item limit, so this catalog cannot grow without a schema change.

For this experiment, semantic reuse is admitted only for four grammatical families of unqualified retention questions about Atlas or Boreal:

src/ragcache/core.py · lines 38–55
def semantic_contract(question: str) -> str | None:
    """Deliberately bounded admission grammar, NOT a general semantic verifier.

    Only unqualified retention questions for two synthetic products can share
    answers by embedding similarity. Everything else uses exact matching.
    """
    text = normalize(question)
    patterns = (
        r"what is the (?:data )?retention (?:period|policy) for (atlas|boreal)",
        r"how long does (atlas|boreal) (?:keep|retain|store) (?:data|records)",
        r"how long (?:is|are) (atlas|boreal) (?:data|records) (?:kept|retained|stored)",
        r"for how long does (atlas|boreal) retain (?:data|records)",
    )
    for pattern in patterns:
        match = re.fullmatch(pattern, text)
        if match:
            return f"retention:{match[1]}:unqualified:v1"
    return None

The returned contract includes the product. Dates, negation, audience qualifiers and arbitrary questions do not receive a semantic contract. They can still use an exact answer under the current permission scope; otherwise, they generate a new answer. Passing the grammar does not remove the separate similarity threshold.

I selected 0.75 after inspecting the fixture, so the benchmark is not a held-out threshold evaluation. One admitted paraphrase scores 0.741 against the canonical question and can still miss that entry. The grammar and threshold have separate jobs: the grammar limits which meanings may share an answer; the vector search finds a candidate within that limit.

For two products and four question patterns, I could also key the cache directly by the parsed intent. I kept vector lookup to test the actual ElastiCache integration. A broader question set would need its own equivalence tests before I would allow semantic reuse.

Valkey's filtered KNN lookup

ElastiCache already provides the vector-search building blocks for read-through semantic caching. The application-specific work here is deciding whose generated answer can be reused, against which corpus version, and what happens during a permission update.

Each cached answer is a Valkey hash. scope and contract are TAG fields; the embedding is a 256-dimensional FLOAT32 HNSW vector with cosine distance:

src/ragcache/aws_adapters.py · lines 109–117
def setup(self):
    try:
        return self.client.execute_command("FT.CREATE", self.INDEX, "ON", "HASH", "PREFIX", 1,
            self.PREFIX, "SCHEMA", "scope", "TAG", "contract", "TAG",
            "embedding", "VECTOR", "HNSW", 6, "TYPE", "FLOAT32", "DIM", 256,
            "DISTANCE_METRIC", "COSINE")
    except valkey.exceptions.ResponseError as exc:
        if "exist" not in str(exc).lower():
            raise

The lookup restricts both tags and asks for three neighbors. Both filter values are server-generated hex digests, so raw client text is never interpolated into the query expression.

src/ragcache/aws_adapters.py · lines 144–157
def nearest(self, scope, contract, vector, threshold):
    # Only server-generated hex digests are interpolated into the query.
    contract_id = digest(contract)
    query = f"(@scope:{{{scope}}} @contract:{{{contract_id}}})=>[KNN 3 @embedding $vec]"
    try:
        result = self.client.execute_command("FT.SEARCH", self.INDEX, query, "PARAMS", 2,
            "vec", struct.pack(f"<{len(vector)}f", *vector), "DIALECT", 2)
        for index in range(1, len(result), 2):
            fields = dict(zip(result[index+1][::2], result[index+1][1::2]))
            if 1 - float(fields[b"__embedding_score"]) >= threshold:
                return self.decode(fields[b"payload"])
        return None
    except (valkey.exceptions.ValkeyError, KeyError, ValueError) as exc:
        raise Unavailable("Vector cache unavailable") from exc

The adapter converts cosine distance into similarity with 1 - distance. The service then compares the returned contract and calls valid_for(). An approximate-search miss leads to generation. A semantic hit still needs a query embedding; an exact hit needs neither embedding nor generation.

The first integration run exposed a compatibility issue: the tested ElastiCache for Valkey 8.2.0 engine rejected the explicit SORTBY form of FT.SEARCH. The cache adapter fell back to generation, which kept the request working but failed the assertion that it was a real semantic hit.

The final authorization read

Revocation can happen after the initial snapshot, while a cache lookup or model call is in flight. Both paths converge on the same final check:

src/ragcache/core.py · lines 223–229
hook("before_final_authorize")
final = read_authority()
if final.authorization_stamp() != initial.authorization_stamp():
    raise Changed("Authorization or corpus changed; retry with fresh context")
if not entry.valid_for(final, self.pipeline, scope):
    raise Denied("Candidate dependencies are not authorized")
hook("after_final_authorize")

If both snapshots validate but their stamps differ, the handler returns 409 context_changed with no answer. A missing authority record, enabled=false, or empty grants returns 403. An authority SDK error returns 503; a warm cache does not override it. Handled Valkey errors allow the request to continue with authorized generation, provided the other dependencies succeed.

Cache writes happen after the final check. Entries have a one-hour TTL. Fresh authority reads determine whether an entry can be reused before that TTL expires; changing permissions does not erase the stored answer.

The public API sends Cache-Control: no-store to tell downstream HTTP caches not to store the response.

Revoking access while Lambda is running

The IAM-only test handler can pause at named barriers. The driver polls a DynamoDB marker until Lambda has reached the selected barrier, commits the permission change, then releases the invocation. That lets the test place the update on a known side of the final check.

For a warm cache, the test pauses after lookup. For a miss, it can pause after generation or immediately before final authorization:

scripts/lab.py · lines 326–331
for phase, warm in [("after_lookup", True), ("after_generate", False), ("before_final_authorize", False)]:
    def concurrent_revoke(phase=phase, warm=warm):
        result = self.race(phase, lambda: self.grant("alice", ["public"]), warm=warm)
        expect(result, 409)
        assert "answer" not in result["body"]
    check(f"controlled revocation race at {phase}", concurrent_revoke)

All three cases returned 409 without an answer. A separate publication race changed the corpus version after generation and also returned 409.

I also tested the other side of the boundary:

scripts/lab.py · lines 339–343
def late_boundary():
    result = self.race("after_final_authorize", lambda: self.grant("alice", ["public"]))
    expect(result, days=90)
    expect(self.query(), days=30)
    return {"boundary": "First response authorized before revocation; late fill is not reusable by revoked user"}

That first response contains 90 days because its final authorization snapshot preceded revocation. Its late cache fill stays in the old namespace. The next request reads the new grants and returns the public 30-day answer.

The final transactional snapshot is the authorization linearization point. It is not atomic with HTTP delivery. Once that read has authorized a response, a later revocation can arrive too late to stop it. That is the behavior the last test expects.

Likewise, rejecting delivery does not undo a Bedrock request already sent with sources authorized at the initial read. This protocol does not cancel in-flight inference or erase answers the user previously received.

model_calls counts completed application-level generate() calls. It does not count SDK retry attempts or billable model requests. The token totals are the usage returned by the successful responses.

Every mode passed the fixture's expected-duration check on all 16 requests. That check looks for the expected 90 days or 120 days substring. It does not evaluate every claim in an answer or establish general RAG accuracy.

server_ms measures the service inside Lambda. It excludes Lambda initialization, the public API/JWT path and the operator's network. The benchmark uses IAM Lambda Invoke; real Cognito and HTTP authentication are exercised separately by the correctness suite. Raw client_ms values include the invocation transport.

There are only 16 sequential samples per mode, no concurrent load and no randomized repeated trials. With nearest-rank p95 on 16 samples, the reported p95 is the largest observation. These numbers describe this run; they are not a production tail-latency estimate.

I would not turn the token reduction into a cost-saving percentage. These totals exclude ingestion, preflight, probes, warmup and security tests, while the cache node and two-AZ Bedrock interface endpoint incur costs while provisioned. At low traffic, that infrastructure can cost more than the saved tokens. The raw requests and summary contain the measured inputs.

Clean up the role after Lambda releases its interfaces

The initial teardown exposed an infrastructure-ordering problem. Terraform removed the execution role before Lambda had finished reclaiming its VPC network interfaces. I restored a temporary role limited to deleting the owned interfaces, waited for reclamation, and removed that role too.

The final Terraform configuration makes the application security group depend on the execution policy, retaining the role while that group still has attached interfaces. It also gives subnet and group deletion 30 minutes. This follows the dependency described in AWS's Lambda ENI cleanup guidance.

That ordering change passed Terraform validation, but I did not deploy the entire stack a second time to validate another full teardown. The completed run's independent service checks confirmed absence across 21 checks, including the temporary role, interfaces, cache, data stores and Terraform-managed resources. What this implementation leaves open

A larger corpus needs a different catalog and retrieval index, with publication versions that also cover newly added documents. Personalization would change the sharing key: identical document permissions are insufficient if private conversation history or a user-specific prompt can affect the answer.

I have not tested concurrent request load, streaming, multi-region authority or contract changes across deployments. There is no cache-fill coordination, so simultaneous misses can generate the same answer more than once. The shared execution role, single cache node and missing per-tenant quotas also need work before this becomes a production service.

Provenance records which sources entered the prompt, but does not establish that the generated answer is true. The checks depend on a trusted authority, publisher and cache writer. Prompt injection and answer quality need separate evaluation.

The regression I would keep is simple: warm the internal answer, change the DynamoDB grant, and send the old token again. For this run, the response changed from 90 days to 30 days without a cache purge. The race tests show exactly how far that result extends.
